# AssemblyAI plugin and dynamic endpointing evaluation

Historical experiment, not the current runtime configuration. The draft now
uses the direct AssemblyAI plugin, fixed profile-based endpointing, and disabled preemptive
generation. See [current configuration](assemblyai.md). The measurements below
retain their original transport and timing conditions.

Evaluated September 8, 2026 against main `588314cb310629a749d0526bc643ae394bfaa595`,
using LiveKit Agents and AssemblyAI plugin 1.8.0. This is local evidence, not a
production deployment or a claim of globally optimal settings.

The subsequent [controlled follow-up](assemblyai-endpointing-followup.md)
compares mode/alpha with identical STT and bounds, alternative STT silence
windows, and targeted repeats. Its 112 valid replays do not establish a dynamic
endpointing advantage; they strengthen the case against lowering the entity
minimum on the tested paused name. Runtime settings remain unchanged.

## Boundaries verified

AssemblyAI's direct plugin emits finalized transcript chunks. LiveKit's audio
turn detector, endpointing strategy, and SDK commit path decide when those
chunks become a conversational user turn. The SDK requires a final transcript
before committing, even when the audio model already has an EOT prediction.
Reducing only LiveKit's delay cannot remove that transcription wait.

The endpointing minimum and maximum are alternative paths, not two sequential
waits. The detector's completion probability selects the learned minimum or
maximum; elapsed silence is deducted. Dynamic endpointing adapts its minimum to
pauses, with the configured minimum as a floor. Replacing endpointing options
recreates that learned state, so STT profile changes must leave it alone.

A longer maximum cannot protect an unfinished phrase when the detector assigns
it a high completion probability. The labeled tests reproduced that failure in
both the old gateway configuration and aggressively finalized direct STT.

## Existing audio comparison

Five saved excerpts were replayed through real STT, local Silero VAD, the full
cloud audio turn detector (`turn-detector-v1`), and the real SDK turn-commit path:
three known-reference fixtures (synthetic, public human speech, and the same
human speech with chatter) plus two caller-channel excerpts from saved calls.
The excerpts total roughly 2.7 minutes per arm. The human clean/noisy pair is not
independent speaker coverage. Only already prepared audio was replayed; the
experiment did not rerun or compare noise-cancellation algorithms.

The initial direct-plugin comparison completed 30 valid replays:

| STT min/max ms | LiveKit endpointing | Transcript errors / 130 reference words | Committed turns |
|---|---|---:|---:|
| Gateway 275/2000 | Fixed 300/600 | 18 | 16 |
| Plugin 100/100 | Fixed 300/600 | 11 | 17 |
| Plugin 100/100 | Dynamic 300/1500, alpha .9 | 11 | 15 |
| Plugin 100/100 | Dynamic 300/2500, alpha .9 | 12 | 14 |
| Plugin 275/275 | Dynamic 300/1500, alpha .9 | 18 | 14 |
| Plugin 128/1280 | Dynamic 300/1500, alpha .9 | 17 | 15 |

These rows do not constitute a controlled comparison of
provider model quality. Chunk boundaries and recognition are variable between
runs. The reference score excludes the private calls, which have no independent
word-level truth labels. Different commit counts also mean aggregate commit
latencies are not matched comparisons; fewer commits are not automatically
better. No speech or tool results were generated by an LLM during these replays.

Every arm encountered one transcription timeout in the same saved call excerpt.
A timeout is reported separately from replay execution validity; it is not
hidden as a successful transcription. SDK warnings and rejected pacing trials
remain in private artifacts. Accepted real-time feed drift was at most 99 ms;
runs exceeding 100 ms were excluded and rerun without concurrent build work.

An earlier 35-replay gateway-only sweep compared fixed and dynamic ranges,
including alpha .7 and .9. It identified transcription-gated waits but lacked
labeled conversational boundaries, so it did not establish an optimal delay or
alpha. Alpha .9 remains the SDK default, not a claimed benchmark winner.

## Labeled pause and complete-answer tests

The portable fixture generator creates one known synthetic answer per case.
Separate prefix/suffix audio surrounds exact 600/1200 ms pauses; scheduling also
has an 1800 ms pause. Fixtures cover scheduling, member digits, date of birth,
ordinary and spelled names, email, and full insurance-plan name. They use a single Mac
Samantha voice, phone-band filtering, and no added Krisp processing. Separate
utterance synthesis can create artificial phrase-final intonation; these are
regression challenges, not estimates of real caller cutoff rates.

Acceptance requires exactly one nonempty committed turn containing the complete
expected value, no premature commit more than 100 ms before the known waveform
end, and no recognized final text left uncommitted. All commits count, including
those after the source ends. A prefix commit just after speech resumes is still
a failure. Digits, dates, spelling, and email are normalized conservatively;
transcript WER alone does not prove the correct value was preserved.

Completion delay is measured from the independently known waveform end.
Latency comparisons use only cases where both configurations preserve the full
answer. Playback/network validity and behavioral acceptance are separate.

### Rejected alternatives

The first 13-fixture comparison used the three scheduling pauses and ten entity
pauses, before adding names and complete-answer holdouts:

| Candidate | Accepted answers / 13 | Split answers | Decision |
|---|---:|---:|---|
| Pinned gateway configuration | 10 | 3 | Baseline has scheduling false positives |
| Direct 100 ms ordinary, 400–500 ms fixed entity chunks; dynamic 300/2500 | 5 | 8 | Reject: new DOB/email/insurance splits |
| Direct 100 ms ordinary, 1000 ms fixed entity chunks; EOT threshold .9 | 10 | 3 | Reject: 1200 ms entity pauses still split |
| Direct 100 ms ordinary, entity 1000/3000; calibrated EOT | 10 | 3 | Preserves entities but about 3.2 s finalization |
| Same 1000/3000 entities, EOT threshold .9 | 13 | 0 | Synthetic benefit; insufficient evidence to override calibration |
| Direct 100 ms ordinary, entity 1500/1500; English EOT threshold .9 | 13 | 0 | Faster entity window, threshold override not selected |

Each row contains 13 execution-valid replays. Non-default threshold warnings
are expected SDK configuration warnings, not transcription failures. The
1000/3000 entity candidate repeatedly finalized around 3.2 seconds after the
known end, so it retained the STT wait this experiment sought to reduce.

A subsequent 23-case paired comparison tested a separate semantic name profile
(450/3500 ms) with the native detector and 1500/1500 ms other entity windows.
The baseline preserved 20/23 answers; that candidate preserved only 18/23.
Both split all three scheduling fixtures; the candidate additionally split
both first/last-name pause fixtures. The earlier first-name transcript was
already present when the EOT prediction for resumed surname speech arrived;
the SDK committed it before the surname final transcript arrived. This was a
new failure even though the name STT silence settings matched the baseline.
The separate name profile was therefore removed. Application profile-reset
logic is not needed to reproduce this race.

The custom .9 threshold is also omitted from the runtime. It protected the
artificial unfinished scheduling phrase, but one voice and a few snippets are
not sufficient to replace calibrated per-language thresholds. Very short STT
segments also sometimes reported other languages, so an English-only override
did not consistently control the short-answer holdouts.

### Final exported configuration

The draft uses the direct plugin with 100/100 ms ordinary STT, 1500/1500 ms
intake/name/ID/email/insurance STT, calibrated LiveKit audio thresholds, and
stable dynamic endpointing 300/2500 ms with alpha .9. The 23 final candidate
replays use the repository's exported options. They are paired with 23 unchanged
controls from the completed previous batch; input hashes and fixture labels are
validated before scoring. Reusing controls does not count as new provider runs.

| Measurement | Pinned baseline | Final candidate |
|---|---:|---:|
| Execution-valid cases | 23/23 | 23/23 |
| Complete answer in exactly one commit | 20/23 | 21/23 |
| Split answers | 3 | 2 |
| Transcription timeout events | 7 | 0 |
| DOB with 1200 ms internal pause: completion delay | 3.81 s | 1.82 s |
| Complete DOB: completion delay | 3.79 s | 1.77 s |
| Complete insurance name: completion delay | 3.33 s | 1.69 s |
| Complete short name: completion delay | 0.57 s | 1.86 s |
| Complete short negative answer: completion delay | 0.63 s | 2.53 s |

Across the **20 fixtures accepted by both configurations**, the median paired
completion-delay change was **1.00 second faster**. This field-heavy synthetic
suite is not the distribution of real calls. The gain must not be described as
an overall production latency improvement or attributed to dynamic endpointing
alone: the STT segmentation settings and provider transport also changed.

All twelve paused name/entity fixtures were preserved by the final candidate.
The 1200/1800 ms unfinished scheduling fixtures still split. Its 600 ms version
passed in this run but split in earlier runs using equivalent ordinary settings,
so that single pass is not robust evidence of a fix. The short negative answer
had low model completion probability and therefore selected the 2500 ms ceiling.
A simple name waited for the longer intake transcript window. These are material
regressions, retained rather than hidden in the aggregate speed gain.

Eight selected final cases were replayed again: both paused names, a complete
name, the 1200 ms DOB/email/insurance answers, a short negative answer, and the
1200 ms scheduling continuation. Both passes preserved 7/8 answers; scheduling
still split. The complete name took 1.86/1.79 seconds and the negative answer
2.53/2.54 seconds, confirming those delay penalties in this small holdout.
Maximum pacing drift across the final comparison and repeats was 19 ms.

The final five saved-audio replays also completed with the exported ordinary
settings and unchanged input hashes: 13 committed turns, 11 transcript word
errors over 130 known-reference words, one SDK warning, and one transcription
timeout in the same call excerpt as before. Maximum feed drift was 10 ms. These
results repeat the ordinary-profile comparison; they do not exercise the
application's prompt-dependent profile changes on the recorded calls.

This remains a **draft experiment**, not an optimal or ready-to-deploy
configuration. Before promotion, resolve the short-answer/name delay tradeoff
and validate natural multi-turn conversations, partial answers, and longer
entity pauses. A single ceiling cannot simultaneously guarantee immediate
short answers and preserve every uncertain continuation.

## Live profile-update proof

A separate live plugin stream used the actual application profile controller
while feeding three known complete answers. It changed to insurance, reset on
commit, changed to intake, reset again, then transcribed an ordinary closing
answer. All three exact normalized answers were preserved; each prompted
profile remained active through its final transcript. Final-transcript delays
were 1722/1746/371 ms, with 6 ms maximum feed drift. This verifies provider
acceptance of live configuration changes and the return to short ordinary STT
windows. It is a direct-STT/controller check, not a full conversational session.

## ForceEndpoint proof

A separate paired test used the same known synthetic waveform with direct STT
minimum 1000 ms / maximum 5000 ms. Explicitly calling
`SpeechStream.forceEndpoint()` about 267 ms after speech ended produced the final
transcript 217 ms after the call, 938 ms earlier than the unforced control. Both
final transcripts were identical. This establishes that the plugin sends the
provider operation successfully; it does not establish a latency distribution.

LiveKit does not automatically call this method when its audio turn detector
fires. Its public EOT hook is already on the transcript-gated path, so using that
hook to obtain the first missing final creates a circular dependency. The PR
uses standard transcript chunking and endpointing, without an SDK patch or a
second custom turn-completion controller.

## Review and automated checks

- Application checks: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, and
  `pnpm test` passed: 48 files / 1,016 tests. The office-knowledge benchmark was
  42.14 ms against its 250 ms budget.
- Scorer checks: three standard-library Python regression tests passed. They
  reject extended incorrect values, late prefix/suffix splits, missing final
  text, duplicate cases, mismatched audio, inconsistent settings, and incomplete
  paired coverage.
- Standards review: missing private failure artifacts were fixed; no additional
  actionable finding in the final source simplification.
- Spec review: loose entity scoring and unchecked pairing were fixed. The final
  review found no additional blocker to a draft PR, while explicitly retaining
  the behavioral failures above. Aggressive 100–500 ms entity chunks, a semantic name profile,
  and a custom completion threshold were rejected as rollout recommendations.

## Reproduction and limits

See [the replay instructions](../../diagnostics/README.md). Generated audio,
credentials, raw SDK logs, and transcripts stay outside the repository. Each
private result records input SHA-256, concrete provider options, endpointing
options, model identity, predictions, finals, commits, feed completion, pacing,
warnings, and timeouts. Public evidence contains aggregate results only.

Natural-call playback supplies energy-derived historical agent speech markers
to endpointing learning; it does not reproduce a live agent's interruption state.
Labeled cases start fresh sessions and keep one STT profile fixed. The baseline
reproduces pinned provider/endpointing configuration, not the old application's
reset-on-final profile lifecycle. A separate SDK integration regression verifies
that prompt/profile transitions preserve already learned dynamic timing.
Automated preemptive-generation tests verify deferred/cancelled tool execution,
but these audio replays contain no live LLM/TTS, SIP routing, backend operations,
or complete adaptive interruption interaction. No real appointment was changed.

The direct plugin needs `ASSEMBLYAI_API_KEY` provisioned on the deployment target.
English synthetic results do not validate Spanish turn timing or natural accents.
Longer pauses than the tested gaps and completion-model false positives remain
possible. A live conversational pilot is still necessary before broad rollout.

## Subsequent developer-docs audit

The [docs audit](assemblyai-docs-audit.md) found that TTS-input observation could
publish questions before they were played and contaminate follow-up profile
history. Two failing regressions reproduced those errors. Context and remembered
follow-up profiles now advance only from SDK-committed assistant output; early
TTS observation only arms recognition. The historical fixture replays supplied
a known preceding question and do not themselves verify this playback lifecycle.
Silence values and detector thresholds were not retuned by this correction.

After this correction, all 1019 application tests and the typecheck/lint/format
checks passed; the live profile/context path preserved three exact synthetic
answers. See the audit for scope and SDK alignment limitations.
